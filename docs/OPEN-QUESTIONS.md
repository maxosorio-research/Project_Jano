# Open questions

These are not invitations for a coding agent to invent permanent answers. Each should be resolved through a focused implementation spike or ADR.

## 1. Physical `.jano` persistence migration

Closed:
- conceptual entities;
- relative paths;
- stable IDs;
- portability;
- hybrid target: `project.json` bootstrap, SQLite relational state, ordinary
  content/artifact files, and explicit JSON exports.

Open:
- exact SQLite schema and indexes;
- artifact cache/retention policy;
- migration and rollback implementation details.

MVP guidance:
- choose a small reversible implementation behind repositories;
- do not make raw storage a public API.

Current decision after the structured-reader work:

- JSON remains adequate for `v0.1.0-rc.0` and keeps artifacts inspectable;
- the hybrid layout is accepted before alignments become editable or annotations add many small transactional writes;
- `project.json` can remain a portable bootstrap while `state.sqlite` owns relational/query-heavy state;
- per-document source, Markdown, math, and diagnostic artifacts can remain ordinary sidecars;
- do not create a JSON/SQLite dual-write source of truth;
- implement and test the migration before building alignment correction, not during the first synchronized-reader exit test.

## 2. External translation alignment algorithm — deferred after 0.1

Closed:
- align segments, not pages;
- support non-1:1 relationships;
- provide confidence/fallback;
- scroll consumes semantic anchors.

Open:
- first algorithm for existing translated documents;
- whether it uses lexical, sentence-embedding, dynamic-programming, or hybrid matching;
- quality thresholds.

0.1 resolution:
- Jano synchronizes only translations generated by its local pipeline;
- generated source and target records preserve segment IDs and use deterministic structural alignment;
- external translation alignment is not an MVP exit requirement.

Future guidance:
- isolate the external algorithm behind `AlignmentEngine`;
- build deterministic fixtures;
- schedule a design spike before accepting external translations in the UI.

## 3. Translation input normalization in 0.1 — closed

The right side is Markdown generated by Jano's explicit local pipeline. The
readable file is written as `<source-stem>.<target-language>.md`, while structured
artifacts live under `.jano/documents/<document_id>/`. User-authored Markdown and
translated PDFs are not accepted as synchronized 0.1 inputs.

## 4. PDF extraction library details

The goal is logical reading order and segment/source location preservation.

Open:
- exact extraction library/tool beyond PDF.js rendering;
- strategy for multi-column reading order;
- locator representation that best round-trips into the viewer.

The current implementation uses coordinate-aware PDF.js extraction and bundled
English OCR only when native text is deficient. Precise source rectangles and
additional OCR languages remain open.

## 5. Toolbar placement

Minor open UX choice:
- discreet upper reader toolbar is the current default;
- can be adjusted after hands-on testing.

## 6. Licensing implementation

The intended early license policy is PolyForm Noncommercial 1.0.0 and separate trademark policy.

The official PolyForm text is already present. A complete dependency-license
review is still required before public distribution. Trademark wording is
deliberately deferred to the final public-release preparation and does not block
internal `0.1.0-rc.*` tags or synchronization improvements.

This package does not substitute for legal review.
